# RTSP and RTSPS publication

Receive independently generated live media using RTSP/1.0 ANNOUNCE, SETUP and RECORD on the existing optional RTSP/RTSPS listeners. A configured stream (including inherited templates) accepts publications only when its sole input is publish://. The initial receiving profile is interleaved RTP/AVP/TCP, with H264, HEVC, AAC-LC and MPEG audio (MP2/MP3). Plain RTSP uses the same admission as RTSPS; RTSPS encrypts control and media. UDP publication, dynamic stream creation, outbound RTSP push and Digest authentication are later tasks.

Use the existing publisher password query and on_publish callback. Neither viewer nor administration credentials bypass admission. Callback proto is rtsp on either listener; query, socket IP, session identifier, elapsed duration, monotonic request number and received bytes are retained. Policy or media configuration changes revoke the connection, including changes during callback waits. Metadata-only edits retain it. Initial and renewing callbacks have the existing bounded timeout. LB nodes reject publication.

ANNOUNCE and SETUP reserve a shared publisher admission permit but create no media worker. RECORD claims the same per-stream exclusive publication ownership as HTTP, creates exactly one common FFmpeg worker and supplies a regenerated private SDP through its stdin. Every advertised track must be SETUP before RECORD. Playback and publication cannot share a connection. Only live RECORD is supported. Session and URL bindings prevent cross-stream, cross-origin, query substitution and channel aliasing. Disconnect, stall, malformed media, worker exit, teardown or revocation end and reap only the owning worker generation.

The native server validates bounded SDP and RTP/RTCP. Ignore ANNOUNCE network addresses and ports when routing: never connect to advertised resources. Accept only validated codec parameters and bounded track controls, then regenerate a literal loopback SDP. Allocate owned private consecutive decoder port pairs, release their reservations just before starting decoder binding and observe readiness through the Linux socket table without probe bindings. All public media remains inside the TCP/TLS connection. RTP SSRC is pinned by the first valid packet per track. Preserve sender reports only for that identity; forward valid private feedback over the assigned RTCP channel. Interleaved messages remain bounded to 8192 bytes; direct UDP packet bounds are unchanged. Media silence respects the configured input timeout and cannot be concealed by RTCP/control floods.

Existing TS/HLS/native/direct/RTSP delivery and copy or CPU/GPU transcode operate on the same worker. Qualify actual publisher input and independently decode the shared TS output for H264/HEVC with AAC/MP2/MP3, multi-audio and audio-only. Use explicit H264 iGPU qualification only if available. Separate DVB/teletext subtitle SDP tracks are unsupported and rejected; embedded captions follow the existing video pipeline. Do not imply full parity or migration readiness.

Expose truthful enabled publication listener addresses and profiles in capabilities. Existing friendly receive-publication controls retain HTTP URL and gain RTSP/RTSPS URLs when the corresponding listeners are enabled. Do not persist generated listener metadata into stream configuration. Update documentation with standalone FFmpeg examples and remaining gaps. No installed vendor code is used.
