# Streaming recovery and HLS continuity

Continue the approved Streams/Templates/Cluster product and isolated Linux/CDN testing and GitHub publication. Execute inline in an owned worktree. Installed Flussonic remains an optional reverse-engineering reference only; build, normal tests and daemon use independent components. Retain the approved admin design and labeled controls.

## Intended behavior

A failed or stalled input must release its packaging process, close its old continuous bodies, wait a bounded retry interval and try the next configured input. Static streams recover continuously. On-demand local streams and native CDN mirrors recover while their latest actual request/body departure is less than 60 seconds old or a body remains attached. Background recovery never renews demand by itself. Configuration removal/disable and source/policy fences remain authoritative. This is recovery within the existing configured stream/source relationship; unrelated same-name sources are not declared equivalent.

## Worker lifecycle

Retain Engine's serialized ensure/stop lifecycle and one worker per stream. Add a narrow recovery helper for timeout/failure/retry state and an Engine::recover entrypoint that shares ensure logic without touching demand. Count restarts independently of consecutive short failures. First retry waits one second, consecutive failures back off 2/4/8/16/30 seconds, capped at 30; 30 seconds of successful media resets the failure streak. Advance ordered inputs after failure; configuration changes reset the input index. Waiting viewer retries refresh actual demand but cannot bypass cooldown.

The watchdog measures packaging MPEG-TS output progress, including startup. Native `flussonix_input_timeout` is an inherited stream/template integer of 1..300 seconds, default 15. No output within that interval triggers startup_timeout or input_stalled; EOF/error has sanitized input_closed/packaging_failed reasons. Continuous media does not time out. Cancellation from a stop is not a failure. No credential-bearing URLs or arbitrary subprocess stderr appear in error/status fields. Existing M4S/M4F original relay and auth cancellation stay bounded.

Recovery stats expose input_index (zero-based API, one-based UI), restart_count, retry_in_ms, last_error and media_age_ms, alongside existing protocol/PID/status. A pending retry reports retrying; healthy output reports running. readiness must exclude stopped/stalled workers and stale pre-restart files. Reconciliation recovers eligible failed workers without another viewer request, retires idle on-demand workers before considering retry, and rechecks changed config after asynchronous starts so stale snapshots cannot resurrect removed/disabled streams.

## HLS restart behavior

Within a daemon, replacement starts use a sequence greater than the old TS/fMP4 playlist's last segment sequence, even if the wall clock moves backward. Seed with epoch microseconds and maintain an Engine-wide high-water mark, updated from old playlists before deleting output. Each attempt uses a fresh safe generation name for TS/fMP4 segments and its fMP4 init resource. Prepend a discontinuity on replacements. No old media URI may return new attempt bytes. Failed/stopped worker manifests must not be served as fresh output. Independent FFmpeg encodes/muxes once per stream, never per viewer. See [FFmpeg HLS options](https://ffmpeg.org/ffmpeg-formats.html#hls-2).

An established TS/M4 connection closes when its worker fails; reconnection is required. HLS player recovery is qualified by actual playback during an owned worker failure, with an observed interruption rather than a gapless claim. Full seamless failover, origin-equivalence placement, global ownership and new protocol roles remain separate roadmap work.
