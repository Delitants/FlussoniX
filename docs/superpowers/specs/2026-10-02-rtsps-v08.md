# RTSPS v0.8 design

Continue the approved independent protocol direction matrix with encrypted RTSP-controlled TCP playback and authenticated, certificate-verified RTSPS input. Preserve plain RTSP TCP/UDP, existing auth, shared workers and native cluster pulls. This is an architectural transport extension, implemented inline under standing development/test/publication authorization. No official Flussonic runtime/components are introduced.

An optional separate `--rtsps-listen ADDRESS:PORT` requires `--rtsps-cert PATH --rtsps-key PATH`. PEM chain/key are loaded and validated before workers start; malformed/mismatched material and occupied listeners fail startup. TLS 1.2/1.3 use Rustls with ring, no client certificate requirement; viewer URL-token/on_play authorization remains mandatory according to stream policy and uses proto=rtsp. A bounded eight-second TLS handshake consumes the listener's 256-connection limit before any parser/worker admission. Shutdown cancels handshakes, sessions and supervised listeners. Existing parser/body/write/readiness/control/queue limits apply. Encrypted interleaving protects both RTP and RTCP; UDP SETUP on TLS is rejected until SRTP is implemented. Plain listeners reject RTSPS URIs; TLS listeners accept RTSP/RTSPS logical URIs inside the encrypted connection to support verified input bridging. No cleartext TLS fallback.

RTSPS input connects with Rustls and validates chain, validity and DNS/IP identity before a request, token or credential can be forwarded. Default trust uses bundled Mozilla roots; a per-input absolute `flussonix_tls_ca` PEM path replaces that trust store for private PKI. Invalid/missing roots fail closed. The TLS client uses the configured original host for SNI/identity, ten-second connect/handshake deadline, no dangerous verifier or verification-disable setting. Configuration rejects the CA field on other protocols, malformed paths and RTSPS UDP. Templates inherit complete input objects. A normal CA-file field appears for RTSPS URLs and is removed when switching protocols; no JSON editor is added.

To reuse the independent FFmpeg demuxer without trusting its backend-dependent TLS verification, prepare one already-verified upstream TLS connection and a one-shot loopback RTSP bridge per worker. FFmpeg uses the equivalent loopback RTSP URL, preserving path/query/userinfo. One accepted loopback connection, eight-second accept deadline, bounded streaming copy and worker-owned cancellation/Drop stop every bridge and socket; no proxy survives failed FFmpeg spawn, worker stop/replacement or startup error. Logical local RTSP URIs remain inside the verified TLS stream. No credential is sent before successful verification. RTSPS statistics retain the original input protocol. No direct input fallback/downgrade to the original server's plaintext endpoint is permitted.

Tests generate owned temporary CA/server keys with system OpenSSL (not packaged private keys), independently decode H.264/AAC via TLS, assert denial before workers, grant revocation, wrong/expired/untrusted identities with no application bytes, TLS UDP rejection, occupied/malformed-material startup before static workers, hung handshake and active-session shutdown, input-to-HLS decode, bridge lifecycle and config/UI inheritance. Remaining publication/push, direct RTP/SRTP, Basic/Digest viewer auth, exact vendor TLS dialects, GPU and production-scale/migration qualification remain pending.
