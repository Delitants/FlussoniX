## Transport profile

Implement RFC3550 RTP/RTCP with RFC2250 MPEG-TS (MP2T, payload type33, 90kHz) over UDP, independently of RTSP. One transport contains the requested H.264/HEVC and AAC/MPEG LayerII/MP3 plus supported original MPEG-TS subtitle tracks. Initial direct profile is MP2T, not elementary dynamic payload/SDP negotiation, SAP or WebRTC. Explicitly retain those latter profiles as future work. Native Rust packetization shares the processed stream, avoids a per-destination encoding/remux worker and never silently substitutes a different transport.

Input URL rtp://IP:PORT or srtp://IP:PORT binds a unicast IP or joins an IPv4 multicast group. Options under flussonix_rtp: interface (IPv4 address, multicast requires explicit interface), source_ip (optional exact source IP), jitter_ms (0..1000, default50), ttl (1..255 default16), key_file (absolute owner-only regular file, only SRTP). Keys are references, never URL query material. RTP and RTCP use consecutive ports; validate1024..65534. Reject DNS addresses, URL credentials/query/path/fragment and unused/unknown options. IPv6 unicast is supported; IPv6 multicast is rejected clearly in this initial profile. Admission is a configured endpoint/source filter/key, not an invented viewer token handshake. Unencrypted input pins the first structurally valid peer/SSRC; SRTP pins only after authentication. Receiver buffers at most64 packets, waits at most jitter_ms for a gap, tracks duplicate/late/lost packets, handles 16-bit sequence wrap, rejects changed peers/SSRC, malformed RTP/RTCP/TS and oversized packets. Feedback is bounded and sent only to the pinned source IP and negotiated consecutive RTCP source port; never reflect unauthenticated packets. Startup/socket binding is fail-closed and worker-owned; cancellation closes both sockets and awaits tasks. AV watchdog/fallback/recovery remain shared with other inputs.

Native output array flussonix_rtp_outputs: at most4 destinations, each has url, disabled, flussonix_rtp options and max_mbps (1..10000, default100). Destination URL targets RTP and next-port RTCP. Enabled destinations sustain configured input demand, while publish:// still waits for a publisher. Templates inherit or override/clear the entire array. Output sends at most7 TS packets per RTP packet (1328 bytes before protection); native sequence/SSRC/timestamp seeds are random each generation and timestamp progression follows a monotonic 90kHz send clock. Rate limit payload and bound slow writes/queues. Broadcast lag terminates that destination instead of corrupting a shared stream. Send periodic compound sender reports/SDES and consume bounded RTCP feedback; counters represent local socket sends, not remote delivery acknowledgements. No automatic retry with the same SRTP sequence/key context after a transport error; restart requires a fresh generation and fresh session identity.

## SRTP protection

Use independent system libsrtp2 through a narrow dynamic Rust FFI adapter; existing libloading/libc suffice, no proprietary component or custom encryption. Pin stable libsrtp2 ABI using verified2.7 header and layout tests. Suite AES_CM_128_HMAC_SHA1_80, 16-byte key plus14-byte salt (30 bytes, base64 in key file), 128-packet replay window, retransmission disabled. Protect RTP and RTCP independently; authenticate before releasing payloads or pinning peer identity. Wrong keys, tamper, replay, plaintext and malformed authenticated traffic must be rejected. Track authenticated SSRC and refuse additional sources before creating additional lib state. Expose only sanitized availability/status/counters. Key file must be absolute, regular, non-symlink, owner-only and bounded; avoid following symlink at open with O_NOFOLLOW and validate the opened descriptor. Reload on new worker generation only. This statically keyed first profile starts receivers with initial ROC zero; unsignalled late joins after sender sequence rollover require a coordinated fresh sender epoch. Negotiated or configurable initial ROC remains a further profile. No plaintext fallback. New encryption sessions use random SSRC/sequence and derive a fresh sender identity; reuse of identical configured key across independent senders is the operator's key allocation contract. Rekey explicitly replaces worker generation/key reference; unauthenticated automatic key negotiation and DTLS-SRTP remain out of scope.
