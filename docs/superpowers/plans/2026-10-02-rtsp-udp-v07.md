# RTSP UDP v0.7 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task inline.

**Goal:** Authorized, bounded and paced RTSP unicast UDP H.264/AAC playback with independent interoperability evidence.
**Architecture:** Shared timed RTP records feed a per-session delivery enum. A prebound finite UDP pool and pacer reuse the existing connection-owned grant, media subscription and cancellation loop.
**Tech Stack:** Rust/Tokio, existing packetizer and FFmpeg; no new product dependencies.
**Spec:** docs/superpowers/specs/2026-10-02-rtsp-udp-v07.md

## Global Constraints

UDP disabled by default; explicit inclusive 2..256-port range, even first/odd last, all >=1024, bound before workers. Client ports consecutive even/odd >=1024. Rate finite 1..10000 Mbps, default 100; 32 KiB burst. Same TCP peer IP only, no third-party destinations/multicast or mixed transports. At most two tracks/one pending packet per connection, incoming RTCP <=8192 bytes. Existing control/write/deadline/grant/worker/queue limits remain. Preserve vendor-independent runtime, friendly UI and existing source fences. Existing authorization permits owned worktree, isolated deployment and publication; no redundant consent menus.

## Review Focus

- Old RTCP datagrams or failed SETUP must not leak leases, revive another session or redirect its UDP traffic.
- Every datagram/queued/paced wait must retain exact grant/worker cancellation and not starve control under RTCP flood.
- Packed GOP bursts, unusual DTS spacing/large clocks and polling cancellation must preserve packet order without unbounded waits or silent loss.
- Exhausted/occupied pools and IPv4/IPv6 family handling must fail safely while existing TCP sessions remain usable.
- Successful datagram bytes only must feed session/total telemetry; shutdown/replacement must release ports/tasks/viewers.
