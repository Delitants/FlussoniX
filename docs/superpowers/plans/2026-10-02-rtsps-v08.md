# RTSPS v0.8 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan inline with one fresh whole-branch review.

**Goal:** Encrypted authorized RTSPS TCP playback and verified RTSPS input with independent decode and lifecycle evidence.
**Architecture:** Generic RTSP stream session behind bounded TLS accept; verified Rustls upstream feeds a worker-owned single-client loopback bridge for independent FFmpeg ingest.
**Tech Stack:** Rust/Tokio, existing Rustls/ring, independent FFmpeg/OpenSSL tests. Direct tokio-rustls and webpki-roots dependencies promote already resolved libraries; no vendor components.
**Spec:** docs/superpowers/specs/2026-10-02-rtsps-v08.md

## Global Constraints

TLS listeners opt-in; certificate/key validation before workers. TLS1.2/1.3; 256 control/handshake connections per listener, eight-second handshake and bridge accept, ten-second upstream setup, existing RTSP limits. No TLS UDP or verifier bypass/fallback. Upstream CA/hostname/IP verified before application bytes; bridge owned by worker, one loopback client only. Friendly forms, original protocol stats and existing private-source/auth fences preserved. Standing authorization permits isolated deployment/publication; redundant skill approval menus are overridden by developer persistence/user Continue.

## Review Focus

- Incomplete TLS handshake or cancellation must not retain permits/tasks or admit workers.
- Certificate parsing, custom roots and original DNS/IP identity must fail closed before credentials.
- Every failed startup/spawn/retry/replacement must stop bridge sockets and tasks.
- URI aliases and control-session binding must not permit plaintext RTSPS or TLS UDP downgrade.
- TLS writers and native cluster pulls must preserve two-track packet order/auth accounting.
