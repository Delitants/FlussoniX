# Continuous MPEG-TS buffering

FlussoniX shares one unread MPEG-TS backlog per stream across HTTP/HTTPS playback, SRT playback, HTTP/SRT/RTSP publishing, shared TS packaging and MPEG-TS RTP/SRTP output. The backlog holds up to 4 MiB of payload and 32,768 chunks. FFmpeg read sizes vary, so a GOP burst can span many chunks without losing data merely because it crosses 64 reads.

Viewers receive the original bytes in order. Consumed chunks are released as soon as every interested viewer advances or leaves; a stream without TS viewers retains no TS backlog. A new subscription starts at the current live position. Reading a chunk retains its immutable payload independently of the queue.

The byte budget is shared, not multiplied by viewer count. Queue metadata and transport socket buffers also consume memory. A subscriber that exceeds the backlog gets an internal lag error and its current delivery ends; FlussoniX never silently skips missing TS. Other viewers continue independently. Existing authorization revocation, worker cancellation and publishing retry policies remain in effect.

This buffer absorbs short delivery bursts. It does not shape network bandwidth or provide DVR replay, and very high bitrate streams can exhaust the finite budget sooner.

Native HTTP MPEG-TS deliveries emit one structured `native_ts_delivery_end` event on the `flussonix::native_ts` logging target at INFO level. To capture these events while keeping other logs at WARN, set `RUST_LOG=warn,flussonix::native_ts=info` before starting FlussoniX. The reasons distinguish `queue_lagged`, `authorization_revoked`, `worker_stopped`, `queue_closed`, and `body_dropped`. A body drop without a selected terminal branch does not prove a client disconnect or a network error.

Events include a process-local delivery ID, worker PID, elapsed time, missed-record count, byte counters, retained queue size, and cancellation flags. They omit stream names, viewer addresses, URLs, tokens and credentials. `bytes_yielded` counts bytes passed to the HTTP body, not bytes acknowledged by the client. Worker-byte and queue snapshots describe the worker at observation time; they are not an exact socket-backlog measurement. No per-packet logs are emitted. Media bytes and HTTP status/headers are unchanged.

M4S fan-out retains its bounded live history only while M4S subscribers exist. Streams used solely for MPEG-TS, HLS or other outputs do not fill an unused M4S queue, including when their input arrives as whole M4F GOPs. The last M4S subscriber leaving releases that history. A separate bootstrap still supplies metadata and a decodable current GOP to late joins; the M4F segment window remains available independently. Active M4S subscriber byte/record limits and lag handling are unchanged.

Native HTTP/1 MPEG-TS output on the daemon's HTTP and HTTPS listeners interrupts its connection when the original viewer authorization is revoked or its worker stops. This also wakes pending transport writes, releases the delivery's viewer/backlog ownership, and discards unsent socket data with an abortive TCP close. The client can observe a connection reset and must reconnect; bytes already received into client buffers cannot be retracted. Healthy viewers on other connections continue independently. Normal completion, body destruction and queue lag do not by themselves trigger this reset.

Cancellation watchers retain only cloned cancellation tokens. A body registration fences eligibility and abort under the same lock as unregistering, so a retired watcher cannot reset a reused connection. The original listener peer address remains the source of viewer identity; request headers never supply connection cancellation authority. `transport_abort_requested` records a watcher/body-selected transport cancellation request in the single existing delivery event; it does not prove that a reset reached the peer. The first selected cancellation reason is retained, with authorization priority when both tokens are ready. HTTP/2, M4F/M4S output and other endpoint families do not acquire this HTTP/1 TS watcher. The public TLS listener and bounded handshake behavior remain unchanged.
